# Youth Soccer Hybrid Performance Warehouse

**Status:** Architecture baseline approved for implementation
**Repository:** `lo77667/football-prediction-lab`
**Audience:** Data engineering, sports science, coaching, safeguarding, and analytics leadership

## 1. Purpose and design principles

This warehouse combines structured football and physical data with source-backed qualitative observations to support **developmental decision support** for female teenage soccer players. It is not a medical diagnostic system, a psychological assessment instrument, or an autonomous selection engine. Every prediction must be accompanied by data freshness, feature provenance, uncertainty, and a human review path.

The design uses PostgreSQL as the system of record for relational, numeric, and analytical facts. MongoDB stores versioned narrative artifacts and NLP annotations whose shape evolves over time. Both systems use the same **opaque UUID `player_id`** generated by the identity service. Names, contact details, and legal identity attributes remain outside the analytics schema and are never used as model features.

The core principles are:

| Principle | Implementation rule |
|---|---|
| Point-in-time correctness | Every observation has `observed_at_utc` and `available_at_utc`; training features use only records available by the prediction cutoff. |
| Provenance first | Notes, transcripts, extracted markers, and derived features retain source IDs, author role, model version, and review status. |
| Separation of concerns | Identity and consent are isolated from performance data; raw narratives are more restricted than derived aggregates. |
| Developmental framing | Predictions describe current form, readiness, and expected development under stated assumptions; they do not define a player's worth or fixed potential. |
| Human-in-the-loop | A coach or qualified safeguarding professional can accept, annotate, or override an insight. Overrides are logged. |
| Small-data discipline | Temporal validation, regularization, calibration, bootstrap intervals, and ablation tests are required before deployment. |

## 2. Warehouse architecture

```text
Data sources
  ├─ Match provider / analyst feed ───────────────┐
  ├─ GPS, accelerometer, and physical testing ────┤
  ├─ Wellness forms and workload logs ────────────┤
  └─ Coach audio / notes / reports ────────────────┘
                         │
                         ▼
              Ingestion + quarantine layer
                         │
          validation, de-identification, hashing
              ┌──────────┴──────────┐
              ▼                     ▼
     PostgreSQL structured      MongoDB narratives
     facts and feature marts    notes, transcripts,
                                annotations, evidence
              └──────────┬──────────┘
                         ▼
             Point-in-time feature builder
                         │
       quantitative + qualitative + missingness
                         ▼
        temporal training / scoring data products
                         │
          model registry and prediction tables
                         ▼
                Power BI / Tableau semantic layer
```

A production deployment should expose curated views rather than direct access to raw tables. The dashboard should consume `analytics.v_player_daily_decision_support`, while model training should consume a versioned feature snapshot generated by a repeatable job.

## 3. PostgreSQL schema design

The implementation DDL is in [`schemas/postgres/001_youth_player_warehouse.sql`](../schemas/postgres/001_youth_player_warehouse.sql). It creates the following logical schemas and tables.

| Schema / table | Grain | Purpose and key controls |
|---|---|---|
| `core.player` | One row per pseudonymous player | Stores only `player_id`, academy status, preferred position, dominant foot, and cohort metadata. No name or contact data. |
| `core.academy_team` | One row per team or squad | Supports academy, age-band, and season context. |
| `core.player_team_membership` | One row per player-team interval | Effective-dated membership prevents joining a player to the wrong squad. |
| `core.match` | One row per match | Stores kickoff, competition, venue, opponent, surface, and match context. |
| `facts.player_match_performance` | One row per player per match | Stores minutes, starts, position, actions, possession events, defensive events, discipline, and analyst quality checks. |
| `facts.physical_assessment` | One row per test session per player | Stores height, mass, sprint, jump, agility, aerobic, asymmetry, and measurement metadata. Sensitive health-adjacent fields have a stricter role policy. |
| `facts.player_load_daily` | One row per player per date | Stores external load, high-speed running, accelerations, decelerations, session duration, and load-quality flags. |
| `facts.wellness_daily` | One row per player per date | Stores consented self-reported sleep, soreness, stress, mood, and energy. Raw free text is excluded. |
| `governance.consent_record` | One row per consent version | Records assent/parental authorization, purposes, scope, jurisdiction, expiry, withdrawal, and policy version. |
| `governance.data_access_audit` | One row per access event | Records actor, purpose, resource, decision, and timestamp; never stores raw narrative content. |
| `analytics.qualitative_feature_daily` | One row per player-feature-date | Stores reviewed numeric markers derived from MongoDB notes, including confidence, evidence count, missingness, and as-of timestamps. |
| `analytics.player_feature_snapshot` | One row per player per cutoff | Immutable model-ready feature vector with feature-set version and source watermark. |
| `analytics.model_prediction` | One row per player-target-model-run | Stores prediction, interval/calibration metadata, explanation references, and human review status. |
| `analytics.outcome_observation` | One row per player-target-window | Stores future outcomes used as labels, never as predictors before their availability date. |

Important constraints include unique `(player_id, match_id)` performance rows, unique `(player_id, assessment_at_utc, metric_code)` physical observations, non-overlapping membership intervals, `available_at_utc >= observed_at_utc` where both exist, and `available_at_utc <= cutoff_utc` in the feature builder. All timestamps are `TIMESTAMPTZ` and are normalized to UTC at ingestion.

## 4. MongoDB collection design

The MongoDB validator and indexes are in [`schemas/mongodb/coach_narratives_validator.js`](../schemas/mongodb/coach_narratives_validator.js). MongoDB is the source of record for narrative artifacts, not for player identity.

| Collection | Document purpose | Required governance fields |
|---|---|---|
| `coach_notes` | One raw note, audio transcript, or structured observation | `note_id`, `player_id`, `observed_at_utc`, `available_at_utc`, author role, source type, text or encrypted-object reference, consent scope, provenance, redaction status, and schema version. |
| `narrative_reports` | Periodic development report | Reporting window, strengths, concerns, goals, contextual factors, author role, review state, and source note IDs. |
| `nlp_annotations` | Versioned model output over a note | Taxonomy version, marker list, spans/evidence, confidence, model version, language, and human review state. Model output is not treated as ground truth. |
| `qualitative_feature_events` | Normalized, point-in-time feature events | `event_id`, `player_id`, trait, value, confidence, evidence span/reference, `observed_at_utc`, `available_at_utc`, reviewer, and provenance. |
| `ingestion_receipts` | Idempotency and audit record | Source checksum, connector, received time, processing status, retry count, and error class. |

Raw audio and transcript content should be stored as encrypted object references where possible. If text must be stored in MongoDB, use field-level encryption and separate access roles. Do not place direct identifiers or free-form safeguarding disclosures in analytics exports.

## 5. Cross-database linkage

`player_id` is an immutable, randomly generated UUID assigned by the identity service. PostgreSQL enforces it as a primary key in `core.player`; MongoDB stores it as a string or BSON UUID consistently, with a unique index on `note_id` and non-unique indexes on `(player_id, available_at_utc)` and `(player_id, observed_at_utc)`.

There is intentionally no distributed foreign key between PostgreSQL and MongoDB. A reconciliation job checks that every MongoDB `player_id` exists in PostgreSQL, that the player's analytics consent covers the intended purpose, and that revoked or deleted players are quarantined. Joins occur only in the feature-builder service, which emits a reconciliation report containing unmatched IDs, duplicate events, late-arriving data, and consent exclusions.

The join key is never a name, email, date of birth, or device ID. Identity mapping is held in a separately permissioned vault. Any downstream extract uses a stable surrogate key and removes raw identity fields.

## 6. Integrated toolstack

| Capability | Recommended tool | Implementation guidance |
|---|---|---|
| Audio capture and speech-to-text | Otter.ai or a self-hosted/provider STT service | Export transcript plus recording ID, language, speaker role, confidence, and retrieval timestamp. Treat the transcript as untrusted input requiring redaction and review. |
| Structured ingestion | Python, `pydantic`, `pandas`, provider SDKs, and a queue/orchestrator | Validate at the boundary, quarantine bad records, use checksums and idempotency keys, and keep source watermarks. |
| Relational storage | PostgreSQL | Use migrations, `TIMESTAMPTZ`, row-level security, partitioning by season/date when volume warrants it, and curated analytics views. |
| Narrative storage | MongoDB | Use JSON Schema validation, compound indexes, field-level encryption, and separate databases/roles for raw narratives and derived annotations. |
| NLP preprocessing | spaCy, NLTK, `regex`, and a controlled sports-psychology taxonomy | Prefer explicit marker extraction and negation handling over generic sentiment. Retain evidence spans and confidence. |
| Predictive modeling | scikit-learn | Start with regularized linear models, calibrated logistic regression, random forests/ExtraTrees, and HistGradientBoosting. Add more complex libraries only after out-of-sample evidence. |
| Experiment tracking | MLflow or a repository-native run manifest | Record dataset hash, cutoff policy, feature version, model parameters, metrics, subgroup metrics, and approval status. |
| Data quality | Great Expectations or Pandera | Enforce type, range, freshness, uniqueness, consent, and point-in-time tests. |
| Orchestration | Prefect, Dagster, or a managed scheduler | Separate deterministic ingestion from any LLM/NLP judgment step. Every job must be restartable and idempotent. |
| Dashboard | Power BI or Tableau | Publish a governed semantic model from curated views; do not grant direct dashboard access to raw notes. |

A lightweight first release can use Python jobs, PostgreSQL, MongoDB, and scheduled batch runs without introducing a streaming platform. A later scale-up can add object storage, a queue, and a feature store after data volume and latency justify them.

## 7. Converting qualitative notes into quantitative features

Generic sentiment is a weak proxy for performance psychology. The recommended approach is a **controlled marker taxonomy** with explicit evidence and uncertainty. Example markers include confidence, communication, coachability, attentional control, recovery mindset, competitive response, and perceived readiness. They are not clinical diagnoses.

For a note such as “low confidence after conceding early,” the pipeline should produce a versioned event similar to:

```json
{
  "trait": "confidence",
  "value": 0.25,
  "direction": "low",
  "confidence": 0.87,
  "evidence_span": "low confidence after conceding early",
  "context": "post_match",
  "observed_at_utc": "2026-08-20T18:00:00Z",
  "available_at_utc": "2026-08-20T20:00:00Z",
  "review_status": "coach_confirmed",
  "taxonomy_version": "psych_markers_v1"
}
```

A daily feature builder aggregates events using recency weighting and source reliability while preserving the raw counts:

`marker_score = weighted_mean(value, weight = exp(-lambda * age_days))`

The model-ready record should include the score, event count, mean extraction confidence, source diversity, reviewer status, days since last observation, and a missingness flag. Missing observations are not equivalent to high readiness or low confidence; they must remain explicit features. A phrase such as “not observed” is encoded as missing, not as zero.

Negation, conditional language, and context must be handled. “No signs of low confidence” should not create a low-confidence event. “May lack confidence in unfamiliar settings” should create a lower-confidence event with lower certainty and an explicit context. Human review is required for high-impact markers, contradictory notes, and any safeguarding or health disclosure.

## 8. Predictive model logic

The pipeline is a staged, leakage-safe process:

1. **Ingest and validate.** Land structured records and narrative artifacts with source checksums, timestamps, schema versions, and consent scope.
2. **Protect and normalize.** De-identify, redact direct identifiers, normalize units, map positions, and quarantine invalid or late records.
3. **Transcribe and annotate.** Convert approved audio to text, run taxonomy-based NLP, preserve evidence spans, and route uncertain/high-impact annotations for review.
4. **Build point-in-time features.** For each player and cutoff date, aggregate physical, workload, match, wellness, and qualitative events available by that cutoff only.
5. **Create prospective labels.** Define outcomes such as next-90-day coach-reviewed performance change, next-window availability, or development milestone attainment. Labels must be future observations and must not be recycled from the same narrative used as a predictor.
6. **Split by time and player.** Use earlier windows for training, later windows for validation, and a final untouched period for testing. When multiple rows per player exist, use grouped or purged splits to prevent identity leakage.
7. **Train baselines first.** Compare a quantitative-only model, a qualitative-only model, and the combined hybrid model. Require the hybrid model to improve out-of-sample utility without unacceptable calibration or subgroup degradation.
8. **Calibrate and explain.** Produce probability calibration, prediction intervals where feasible, permutation/SHAP-style explanations subject to privacy controls, and a plain-language reason code set.
9. **Review and monitor.** Track drift, missingness, error by age band/position/cohort, calibration, override frequency, and whether coaches over-rely on one score.

For small-to-medium academy datasets, use regularized linear/logistic models as the reference, then compare Random Forest/ExtraTrees and HistGradientBoosting with conservative hyperparameter search. Generalized additive models are useful where monotonic or smooth relationships are expected. Avoid deep learning until the academy has enough longitudinal observations and a defensible external validation plan.

## 9. Strategic enhancements

| Advanced feature | Construction | Guardrail |
|---|---|---|
| Psychological Readiness Index | A weighted, reviewed composite of recent confidence, attentional control, communication, recovery mindset, and coachability markers, adjusted for recency, evidence confidence, and source diversity. | Not a mental-health score. Show components and uncertainty; never use it as a sole selection criterion. |
| Growth Spurt Impact Factor | Compare recent height/leg-length change and maturity-related workload response with the player's own baseline; combine with soreness, asymmetry, sprint trend, and training tolerance. | Require sports-science oversight and measurement consent. Do not infer biological maturity from age alone or expose it broadly to coaches. |
| Development Velocity and Resilience | Estimate within-player slope for role-specific performance and recovery after setbacks, using a hierarchical or mixed-effects baseline and context-adjusted match difficulty. | Use prospective outcomes, minimum-observation thresholds, shrinkage, and confidence intervals; do not reward excessive playing through pain. |

## 10. Privacy, safeguarding, and ethics

Because this system processes data about minors, the academy should complete a data protection impact assessment and document a lawful basis, purpose limitation, retention schedule, deletion workflow, access roles, and international transfer controls. Under GDPR Article 8, online-service consent involving children below the applicable digital-consent threshold may require parental authorization; national implementations differ, so legal counsel must validate the academy's jurisdiction-specific process [1]. The UK ICO specifically highlights children's information, automated decision-making, profiling, sharing, and rights as areas requiring dedicated guidance [2]. The NIST AI RMF provides a useful voluntary structure for governing, mapping, measuring, and managing AI risk [3].

The minimum ethical controls are:

| Risk | Required control |
|---|---|
| Over-collection | Collect only variables tied to a documented coaching or safeguarding purpose; do not ingest social media or unrelated behavioral data. |
| Re-identification | Keep identity in a separate vault, use opaque IDs, restrict exports, and suppress small-cell subgroup views. |
| Harmful labeling | Use developmental language, show evidence and uncertainty, allow correction, and prohibit fixed “potential” labels. |
| Automated exclusion | Predictions are recommendations only. A qualified human must review adverse decisions and record rationale. |
| Sensitive disclosures | Route safeguarding/health disclosures to authorized professionals; exclude them from ordinary ML features unless explicitly approved. |
| Bias | Monitor performance and calibration across age band, position, cohort, disability status where lawfully and ethically available, and other relevant groups. |
| Data drift | Display freshness and missingness; do not silently backfill historical features with future information. |
| Retention | Define separate retention for raw audio, transcripts, notes, derived features, predictions, and audit records; honor withdrawal and deletion requests. |

## 11. Dashboard specification

The dashboard should be a coach-facing decision-support surface with role-based pages. It should never expose raw psychological narratives by default.

| Page | Key metrics and visuals | Daily coaching decision |
|---|---|---|
| Squad overview | Availability, readiness trend, training load versus rolling baseline, data freshness, and alerts by severity | Who needs a check-in or modified session today? |
| Player detail | Role-normalized match trend, physical trend, workload ratio, readiness components, prediction interval, and recent reviewed evidence | What is changing for this player, and what action is proportionate? |
| Training planning | Session load, recent high-speed efforts, soreness/energy, minutes forecast, and position-specific constraints | Who can tolerate intensity, and who needs recovery or monitoring? |
| Development trajectory | 4/8/12-week slopes, skill-area radar, milestone progress, and within-player percentile bands | Is the player's development moving in the intended direction? |
| Model trust | Calibration plot, confidence distribution, missingness, drift, subgroup metrics, and override rate | Can staff trust today's signals, or should they rely more heavily on direct observation? |
| Safeguarding/admin | Consent status, expiry, withdrawal queue, access audit, and data-quality exceptions | Is this data permitted and safe to use? |

Use conditional formatting sparingly. A red flag should mean “review required,” not “player is bad.” Tooltips should define every metric, show the as-of time, and link to a permitted evidence summary. Dashboard extracts should use row-level security and should omit raw note text, names, contact data, and precise health measurements unless the viewer's role explicitly permits them.

## 12. Delivery milestones and acceptance criteria

| Milestone | Acceptance criteria |
|---|---|
| Foundation | PostgreSQL migrations and MongoDB validators apply cleanly; IDs, timestamps, consent fields, and indexes are tested. |
| Ingestion | Replays are idempotent; invalid records are quarantined; source checksums and watermarks are recorded. |
| Qualitative features | Taxonomy extraction handles negation, confidence, missingness, evidence spans, and human review. |
| Hybrid model | Quantitative-only and hybrid baselines are compared on a temporal holdout with calibration and subgroup metrics. |
| Safeguarding | DPIA, consent matrix, retention schedule, role matrix, deletion test, and incident procedure are approved before real data. |
| Dashboard | Coaches can view current state, trends, uncertainty, freshness, and reason codes without seeing unauthorized raw narratives. |
