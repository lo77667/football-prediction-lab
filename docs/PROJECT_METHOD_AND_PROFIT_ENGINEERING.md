# مختبر توقعات كرة القدم: المنهجية والهندسة الموجهة للربح

## الملخص التنفيذي

هذا المستودع مختبر بحثي قابل للتدقيق لتقدير احتمالات أسواق كرة القدم، مع أولوية لمسار **BTTS (كلا الفريقين يسجلان)**. تم اعتماد ثقافة **الهندسة الموجهة للربح**: لا يعني ذلك مطاردة نسبة إصابات أو دقة ظاهرية، بل بناء احتمالات قابلة للمعايرة، واختبار القيمة الاقتصادية بعد إدخال الأسعار الموثوقة، ورفض أي إطلاق لا تدعمه بيانات مستقلة.

الحالة الحالية محلية وshadow-only. `commercial_release=false`، ولا ينفذ النظام مراهنات أو معاملات أو تحديد حصص. لا ينبغي اعتبار أي نتيجة تاريخية أو smoke fixture دليلًا على الربحية المستقبلية.

## الهدف وحدود الادعاء

الهدف هو تحسين جودة القرار الاحتمالي قبل بداية المباراة. المقياس الأساسي ليس accuracy وحده، بل Brier score وlog loss والمعايرة والثبات عبر مواسم ودوريات لم تستخدم في الاختيار. لا يمكن إثبات الربحية دون بيانات odds موثقة، وتكاليف، وانزلاق سعري، وفترة shadow مستقلة؛ لذلك يبقى الاختبار الاقتصادي حاجزًا منفصلًا عن نموذج التنبؤ.

## البنية الحالية

يمر المسار التشغيلي بالمراحل التالية: جمع بيانات ذات provenance، إنشاء لقطة زمنية قبل kickoff، بناء ميزات pre-match، تدريب نموذج، إصدار وحفظ التوقع في ledger، كشف النتيجة لاحقًا، ثم تقييم الأخطاء والمعايرة. تمنع العقود `TARGET_COLUMNS` و`POST_MATCH_AUDIT_COLUMNS` ومراجعات temporal leakage استخدام نتيجة المباراة أو إحصاءاتها اللاحقة كمدخلات.

المصادر الأربعة المعرفة حاليًا هي OpenLigaDB وSportScore وfootball-data.org وTheSportsDB. الشبكة مغلقة افتراضيًا، والمصادر الخارجية لا تدخل التقييم قبل فحص الترخيص والتغطية والتكرار والوقت والبصمة. موسم `2526` محمي من tuning/selection، وموسم `2627` محجوز كـfuture holdout.

## مراحل التحسين المنفذة

### المرحلة الأولى: خط أساس إحصائي

تم الاحتفاظ بنماذج Poisson الحالية لتقدير معدلات الأهداف والبطاقات. نموذج الأهداف يسمح باشتقاق احتمال BTTS من معدلي أهداف المضيف والضيف بدل بناء احتمالات متناقضة لكل سوق.

### المرحلة الثانية: نماذج تعلم آلي جدولية

أضيفت واجهة موحدة لنماذج BTTS في `src/football_prediction_lab/models/ml_btts.py`. تشمل الواجهة Logistic Regression كخط أساس قابل للتفسير، وHistGradientBoosting لالتقاط اللاخطية دون اعتماد native إضافي، وExtraTrees لاكتشاف التفاعلات بين الميزات. تتحقق الواجهة من وجود الميزات، ومحاذاة target، ووجود الفئتين، وقيم finite، وتنتج احتمالات مقيدة إلى `[0,1]`.

تستخدم الإعدادات regularization و`min_samples_leaf` محافظًا لتقليل overfitting على عينات كرة القدم الصغيرة. يجب اختيار المعاملات داخل inner time folds فقط.

### المرحلة الثالثة: الدمج والمعايرة

أضيفت دالة `blend_probabilities` لدمج احتمالات النماذج، وتقبل أوزانًا صريحة يجب تحديدها من out-of-fold predictions داخل validation. لا يجوز تعلم الأوزان من future holdout. يظل Poisson مرجعًا مستقلًا، ويُرفض ensemble إذا لم يحسن Brier وlog loss والمعايرة والثبات.

المعايرة المقترحة هي Platt scaling أو Isotonic داخل كل fold زمني، مع reliability tables وECE. لا تستخدم المعايرة نتيجة مستقبلية أو بيانات ظهرت بعد وقت التنبؤ.

### المرحلة الرابعة: التقييم الاقتصادي

بعد تفعيل odds بمصدر موثق، يحسب النظام القيمة المتوقعة فقط بعد تنظيف الأسعار وتحديد وقت توفرها. لا يجوز اعتبار edge ربحًا. يجب اختبار النتائج بعد خصم الهامش، والعمولة، والانزلاق، وحدود السيولة. تبقى ROI وEV وstake sizing محظورة من المسار التجاري الحالي حتى يمر gate مستقل.

## استراتيجية التقييم

يستخدم التقييم nested walk-forward. تقيس outer folds الأداء النهائي، بينما تستخدم inner folds اختيار النموذج والمعاملات والأوزان. تجمع bootstrap على مستوى `match_id`، وتقسم النتائج حسب الموسم والدوري وتوفر التاريخ وقوة الفرق. تسجل كل تجربة نسخة الكود ونسخة الميزات ونسخة السياسة وmanifest والبصمات.

يجب مقارنة Poisson وLogistic وHistGradientBoosting وExtraTrees وensemble في جدول موحد يشمل Brier وlog loss وECE وعدد الصفوف وفواصل الثقة. لا يعتمد نموذج جديد بسبب تحسن accuracy منفردًا أو بسبب موسم واحد.

## تعريف الربح هندسيًا

الهندسة الموجهة للربح تعني ترتيب الأولويات كالآتي: سلامة الزمن والبيانات، احتمال صحيح ومعاير، قياس uncertainty، اختبار مستقل، ثم قيمة اقتصادية قابلة لإعادة الإنتاج. أي نموذج يفشل provenance أو المعايرة أو الثبات يرفض حتى لو حقق عائدًا ظاهريًا في عينة صغيرة.

معادلة القرار المستقبلية، عند توفر سعر decimal موثق `o` واحتمال معاير `p`، هي `EV = p * o - 1` قبل تكاليف التنفيذ. لا يستخدم هذا الحساب إلا بعد إثبات وقت توفر السعر، وإزالة الهامش، وتحديد قواعد اختيار لا تنظر إلى النتيجة.

## ما تم التحقق منه

تم تشغيل Ruff وcompileall وgit diff check بنجاح بعد التحديثات. أضيفت اختبارات للنماذج الجديدة للتحقق من حدود الاحتمال، حتمية الدمج، ورفض القيم غير الصالحة. ما يزال المسار التجاري غير مفعل، وهذا مقصود وليس نقصًا.

## المخاطر والقيود

البيانات المحلية التاريخية ليست جزءًا من Full Source Bundle، لذلك لا يمكن إصدار benchmark جديد موثوق من checkout خالٍ من البيانات. جودة النموذج مرتبطة بجودة kickoff timestamps وتغطية الفرق والتراخيص. الأخبار النصية والإصابات تحتاج مصدرًا مرخصًا ووقت توفر مثبتًا. نجاح API واحد لا يثبت جودة المصدر أو ربحية السوق.

## خطة التشغيل التالية

الخطوة التالية هي توفير snapshots مرخصة مع manifest وSHA-256، ثم تشغيل nested walk-forward للنماذج الجديدة دون لمس future holdout. بعد ذلك تُقاس المعايرة وتُجرى فترة shadow حقيقية، ثم فقط يفتح gate اقتصادي منفصل. لا يفتح أي token تجاري أو إرسال Telegram إطلاقًا تلقائيًا؛ يجب أن تبقى الأسرار في GitHub Actions Secrets أو مخزن أسرار خارجي.
