# قائمة API والأسرار المطلوبة

> لا تضع أي token أو API key داخل Git أو ملفات `configs/`. أضف القيم في GitHub: **Settings → Secrets and variables → Actions → New repository secret**، كما توضح الصورة المرفقة.

## مطلوب لتفعيل مسار البيانات الخارجي

| الخدمة | السر المطلوب | اسم GitHub Secret | مكان الاستخدام | الحالة الحالية | ملاحظات |
|---|---|---|---|---|---|
| football-data.org | API token | `FOOTBALL_DATA_API_TOKEN` | Header باسم `X-Auth-Token` | مفقود | مطلوب عند تفعيل الشبكة، ويجب مراجعة الخطة والحدود والترخيص |
| TheSportsDB | API key | `THESPORTSDB_API_KEY` | ضمن مسار الطلب حسب adapter | مفقود | مطلوب فقط عند اعتماد المصدر وفحص الترخيص والتغطية |

## خدمات لا تحتاج token

| الخدمة | السر | الحالة | ملاحظات |
|---|---|---|---|
| OpenLigaDB | لا يوجد | مهيأ لكن الشبكة مغلقة افتراضيًا | المصدر مجاني ظاهريًا لا يعني صلاحية إعادة التوزيع؛ يجب فحص التغطية والاتفاقية |
| SportScore | لا يوجد في الإعداد الحالي | مهيأ لكن غير معتمد تجاريًا | يتطلب attribution حسب الإعدادات؛ لا يدخل التقييم مباشرة قبل readiness |

## أسرار اختيارية أو مؤجلة

| التكامل | متغير البيئة/السر | الاستخدام | القرار الحالي |
|---|---|---|---|
| The Odds API | `THE_ODDS_API_KEY` | odds وbenchmark اقتصادي | مؤجل؛ لا يفتح `EV` أو `ROI` تلقائيًا |
| OpenAI | `OPENAI_API_KEY` | adapter للتحليل المساعد | اختياري، وليس مطلوبًا لمسار BTTS الأساسي |
| Telegram | `TELEGRAM_BOT_TOKEN` | إرسال الإشعارات | مؤجل؛ المسار الحالي dry-run/shadow فقط |
| RAGFlow | `RAGFLOW_API_KEY` و`RAGFLOW_API_URL` | سياق واسترجاع نصي | غير مطلوب للنموذج الأساسي ومؤجل |
| Ollama | `OLLAMA_URL` | inference محلي | ليس token؛ القيمة الافتراضية محلية `http://127.0.0.1:11434` |
| قاعدة بيانات خارجية | `CONFIG_DB_URL` | إعدادات/تشغيل خارجي | غير مطلوب؛ التخزين المحلي الحالي هو الافتراضي |

## أسرار لا يجب إضافتها

لا تضف متغيرات مثل `FORBIDDEN_KEY` أو `TARGET` أو `RESULT` أو `ODDS` إلى payloads أو audit logs. هذه الأسماء جزء من حواجز التحقق وليست أسرار تكامل. لا تنسخ أي token يظهر في كتالوج عام أو رابط غير رسمي.

## خطوات الإضافة الآمنة

1. افتح إعدادات المستودع في GitHub.
2. انتقل إلى **Secrets and variables → Actions**.
3. أنشئ فقط الأسرار التي ستستخدمها في workflow محدد.
4. استخدم الاسم الحرفي الموجود في الجدول.
5. لا تطبع السر في logs، ولا تضعه في command-line arguments أو artifact.
6. فعّل `allow_network` صراحة في workflow بعد مراجعة المصدر؛ الإعداد الافتراضي في المشروع هو `false`.
7. شغّل readiness فقط، ثم تحقق من provenance والتغطية والوقت قبل إدخال البيانات في التقييم.
8. دوّر المفاتيح دوريًا واحذف أي secret لم يعد ضروريًا.

## الحد الأدنى قبل أي اختبار اقتصادي

يلزم توفر `FOOTBALL_DATA_API_TOKEN` أو مصدر snapshot مرخص بديلًا، و`THE_ODDS_API_KEY` إذا كان benchmark الأسعار مطلوبًا، مع manifest يتضمن وقت الالتقاط والبصمة والترخيص. لا يكفي وجود الأسرار؛ يجب أن تمر البيانات عبر فحوص المصدر، والـschema، والتكرار، والتسرب الزمني، وفترة shadow مستقلة.

## مصدر الأسماء داخل المشروع

الأسماء أعلاه مستخرجة من `configs/external_sources.yaml` و`docs/ARCHITECTURE_README.md` و`docs/nqbe_mvp.md` وملفات adapters. بعض التكاملات مذكورة كمسارات مؤجلة وليست متطلبات للإصدار المحلي الحالي.
