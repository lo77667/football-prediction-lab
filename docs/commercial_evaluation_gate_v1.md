# Commercial Evaluation Gate v1

**المشروع:** Football Prediction Commercial Engine  
**النطاق:** تحليل وصفي ومحاكاة قابلة للتدقيق فقط  
**التنفيذ المالي:** غير موجود  
**الهدف:** منع إعلان أي مقارنة model-versus-market قبل تحقق الهوية الزمنية والمصدرية والإحصائية.

## قرار التصميم

اعتمد المالك الكمي أن الأولوية التجارية الأولى ليست إضافة نموذج جديد، بل إنشاء بوابة قبول تمنع خلط الاحتمال النموذجي بالاحتمال السوقي غير الموثق. لا تُسمى النتيجة ربحًا، ولا تُستخدم لإرسال أمر أو تحديد stake أو حساب ROI. القيمة النظرية، عند توفر بيانات مؤهلة، تبقى وصفًا مشروطًا بجودة المصدر والعمولة والبروتوكول المعلن.

## شروط القبول

| الشرط | السلوك |
|---|---|
| هوية التوقع | يجب تطابق `prediction_id` و`match_id` و`market` و`market_definition` |
| الزمن | يجب أن يكون snapshot قبل `issued_at` وقبل kickoff؛ snapshot بعد الإصدار مرفوض |
| نوع السعر | `opening` و`latest_pre_match` منفصلان؛ `closing` مرفوض في بروتوكول pre-match |
| provenance | المصدر، النسخة، provenance ID، SHA-256، وسياسة إعادة الاستخدام إلزامية |
| المطابقة | kickoff المصدر يطابق المرجع ضمن tolerance معلنة؛ لا توجد مطابقة بالفرق وحدها |
| السوق | يلزم نتيجتان مميزتان للسوق الثنائي؛ الأسواق الأخرى تحتاج method صريحة |
| holdout | الموسم `2526` مرفوض قبل المقارنة إذا مرره المستدعي كـprotected season |
| القرار | القبول يعيد IDs وoverround والاحتمال السوقي؛ الرفض يعيد أسبابًا قابلة للتدقيق |

## الوحدات المنفذة

أُضيف `commercial_gate.py` بوصفه نقطة قبول واحدة للتوقعات والـsnapshots. ويُستدعى `audit_odds_snapshots` قبل حساب التطبيع، ثم تُطبق قاعدة السوق الثنائي. أُضيف `commercial_report.py` لتجميع المقارنات حسب الموسم والسوق ونوع odds والمصدر، مع رفض 2526 قبل أي grouping، وإرجاع status حذر مثل `indeterminate` عندما يعبر فاصل الثقة الصفر.

تعمل `paired_bootstrap_comparison` على صف واحد لكل مباراة، وتعيد أخذ `match_id` كوحدة. لا تسمح الدالة بتكرار المباراة، فلا يمكن أن يسيطر سوق متعدد selections على فاصل عدم اليقين بسبب تكرار الصفوف.

## نتائج التحقق المحلي

بعد إضافة البوابة والتقرير المجمّع، اجتاز المشروع **89 اختبارًا**، وRuff، و`compileall`، و`git diff --check`. الاختبارات الاصطناعية موسومة في suite فقط، ولم تدخل أي قياس حقيقي أو تقرير ربحية.

## حدود الإصدار

هذا الإصدار لا يثبت الربحية ولا صلاحية استراتيجية مالية. ما زال benchmark الاقتصادي الحقيقي مؤجلًا ما لم يقدم المستخدم أو مصدر مرخص snapshots منفصلة تحمل وقت الالتقاط وprovenance وحقوق إعادة الاستخدام. لا يُسمح للطبقة الحالية بإنشاء stake sizing أو Kelly أو أوامر تنفيذ أو توصيات للمستخدم.

## التحسين التالي المقترح

بعد تثبيت البوابة، التحسين المنطقي التالي هو **snapshot ingestion adapter بواجهة provider-neutral** يقرأ ملفات metadata-only أو مصادر مرخصة خارج Git، ويصدر schema موحدًا وmanifestًا دون حفظ أسرار أو اختيار bookmaker بعد ظهور النتائج. لن يعتمد هذا التحسين على 2526، ولن يفتح benchmark اقتصاديًا قبل اجتياز شروط المصدر والترخيص والزمن.

## التحسين التالي المنفذ: provider-neutral ingestion adapter

أُضيف `evaluation/odds_ingestion.py` كطبقة إدخال محلية محايدة للمصدر. تقرأ الطبقة JSONL فقط من مسار يحدده المستدعي، وتحسب SHA-256 للملف، وتثري السجل بالـhash عند غيابه، ثم تمرره إلى `OddsSnapshot` الصارم. لا تنزّل الطبقة أي مصدر، ولا تحفظ أسرارًا، ولا تتعامل مع مصدر غير قابل لإعادة الاستخدام بوصفه بيانات صالحة.

يسجل `IngestionManifest` المسار والبصمة ونسخة المصدر وحالة الترخيص وعدد الصفوف المقروءة والصحيحة والمرفوضة وأسباب الرفض وعدد صفوف الموسم المحمي. يُرفض `2526` قبل قبول السجل، ويمكن تمرير مجموعة مواسم محمية مخصصة في الاختبارات أو البروتوكولات المستقبلية. لا يشارك هذا المسار في اختيار bookmaker بعد النتيجة، ولا يضيف forward-fill أو fallback سعريًا.

أضيفت اختبارات للـhash والmanifest، وسياسة المصدر غير القابل لإعادة الاستخدام، وحماية 2526، والملف المفقود. أصبحت نتيجة الاختبارات المحلية **94 اختبارًا** بعد إضافة هذا التحسين، مع بقاء benchmark الاقتصادي الحقيقي مؤجلًا حتى وصول snapshots مرخصة ومؤرخة.

## قفل المصدر قبل النتيجة

أُضيف `source_policy.py` لتعريف `SourceSelectionPolicy` بمصدر وسوق ونوع odds ووقت إعلان سابق للـkickoff. يطبق `apply_source_selection_policy` السياسة قبل أي مقارنة، ويرفض closing ويُسجل المصادر أو الأنواع غير المطابقة بدل اختيار أفضل provider بعد ظهور outcome. لا تقرأ السياسة أي target أو نتيجة، ولا تنفذ forward-fill أو fallback سعريًا.

أضيفت اختبارات تثبت أن مصدرًا غير معلن ونوع odds غير معلن يُستبعدان، وأن السياسة المعلنة عند kickoff أو بعده مرفوضة. ارتفعت suite المحلية إلى **98 اختبارًا** مع بقاء CI البعيد runner-level failure بلا steps قابلة للقراءة.


## provenance bundle للـledger

أُضيف `selection_provenance.py` لبناء `SelectionProvenance` metadata-only يضم `policy_id` و`policy_sha256` وIDs وبصمات snapshots والسوق والمصدر ونوع odds. يتحقق builder من أن السياسة أُعلنت قبل أو عند أقدم capture، وأن كل snapshot يطابق السوق والمصدر ونوع السعر. لا يحتوي bundle على `actual` أو target أو outcome.

يوفر `verify_selection_provenance` تحققًا fail-closed؛ فإذا تغيرت السياسة أو snapshot أو ترتيب الهوية، يفشل التحقق بدل قبول ledger غير قابل لإعادة البناء. بعد هذا التحسين اجتازت suite المحلية **101 اختبارًا**، مع استمرار عدم توفر benchmark اقتصادي حقيقي وعدم تنفيذ أي إجراء مالي.

## readiness no-go gate

أُضيف `readiness.py` لإخراج قرار صريح من ثلاث حالات: `no_go` عند غياب تحقق المصدر، و`research_only` عند نقص العينة أو بقاء edge غير محسوم، و`conditional` عند اجتياز الشروط الوصفية فقط. حتى الحالة `conditional` تحمل `ready_for_financial_execution: false` دائمًا؛ فهي لا تعني ربحية ولا إذنًا بالمراهنة.

يفشل gate إذا دخل موسم محمي، ويشترط حدًا أدنى معلنًا لصفوف المباريات، ويتطلب `edge_status` غير `indeterminate` أو `unavailable`. بعد إضافة هذه الطبقة اجتازت suite المحلية **106 اختبارات**، مع استمرار الفصل بين الدليل الإحصائي والقرار المالي.

## audit-only decision ledger

أُضيف `decision_ledger.py` لإنشاء أحداث JSONL حتمية تربط `GateDecision` بحالة readiness وpolicy hash وبصمات snapshots. النموذج يفرض `financial_execution: false` و`outcome_recorded: false`، ويستخدم `extra="forbid"` لمنع إدخال `actual` أو `target` أو `roi` أو `stake` ضمن الحدث. يرفض الكاتب تكرار `event_id` ويرتب الأحداث حسب الهوية قبل الكتابة.

هذا السجل مخصص للتدقيق وإعادة البناء فقط، ولا يمثل أمرًا ماليًا أو توصية. اختبارات الوحدة تثبت ثبات الترتيب وارتباط provenance وعدم وجود الحقول المالية، وبلغت suite المحلية **109 اختبارات** قبل التحقق الشامل.

## robustness للمقاييس الاحتمالية

أضيفت اختبارات تغطي احتمالات `0` و`1` مع clipping آمن للـlog-loss، وفئة هدف واحدة يجب أن تعيد ROC-AUC وAverage Precision والمعايرة كـ`null` بدل ادعاء فصل، واختبار حتمية لنفس المدخلات. هذه fixtures اصطناعية للاختبار فقط، ولا تغير تقييم holdout ولا تقدم دليلًا تجاريًا.
