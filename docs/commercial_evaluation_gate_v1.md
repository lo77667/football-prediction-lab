# Commercial Evaluation Gate v1

**المشروع:** Football Prediction Commercial Engine  
**النطاق:** تحليل وصفي ومحاكاة قابلة للتدقيق فقط  
**التنفيذ المالي:** غير موجود  
**الهدف:** منع إعلان أي مقارنة model-versus-market قبل تحقق الهوية الزمنية والمصدرية والإحصائية.

## قرار التصميم

اعتمد المالك الكمي أن الأولوية التجارية الأولى ليست إضافة نموذج جديد، بل إنشاء بوابة قبول تمنع خلط الاحتمال النموذجي بالاحتمال السوقي غير الموثق. لا تُسمى النتيجة ربحًا، ولا تُستخدم لإرسال أمر أو تحديد stake أو حساب ROI. القيمة النظرية، عند توفر بيانات مؤهلة، تبقى وصفًا مشروطًا بجودة المصدر والعمولة والبروتوكول المعلن.

## شروط القبول

| الشرط | السلوك |
|---|---|
| هوية التوقع | يجب تطابق `prediction_id` و`match_id` و`market` و`market_definition` |
| الزمن | يجب أن يكون snapshot قبل `issued_at` وقبل kickoff؛ snapshot بعد الإصدار مرفوض |
| نوع السعر | `opening` و`latest_pre_match` منفصلان؛ `closing` مرفوض في بروتوكول pre-match |
| provenance | المصدر، النسخة، provenance ID، SHA-256، وسياسة إعادة الاستخدام إلزامية |
| المطابقة | kickoff المصدر يطابق المرجع ضمن tolerance معلنة؛ لا توجد مطابقة بالفرق وحدها |
| السوق | يلزم نتيجتان مميزتان للسوق الثنائي؛ الأسواق الأخرى تحتاج method صريحة |
| holdout | الموسم `2526` مرفوض قبل المقارنة إذا مرره المستدعي كـprotected season |
| القرار | القبول يعيد IDs وoverround والاحتمال السوقي؛ الرفض يعيد أسبابًا قابلة للتدقيق |

## الوحدات المنفذة

أُضيف `commercial_gate.py` بوصفه نقطة قبول واحدة للتوقعات والـsnapshots. ويُستدعى `audit_odds_snapshots` قبل حساب التطبيع، ثم تُطبق قاعدة السوق الثنائي. أُضيف `commercial_report.py` لتجميع المقارنات حسب الموسم والسوق ونوع odds والمصدر، مع رفض 2526 قبل أي grouping، وإرجاع status حذر مثل `indeterminate` عندما يعبر فاصل الثقة الصفر.

تعمل `paired_bootstrap_comparison` على صف واحد لكل مباراة، وتعيد أخذ `match_id` كوحدة. لا تسمح الدالة بتكرار المباراة، فلا يمكن أن يسيطر سوق متعدد selections على فاصل عدم اليقين بسبب تكرار الصفوف.

## مراجعة المالك والمساعد

| الدور | المراجعة |
|---|---|
| المساعد / Lead Developer | نفذ بوابة القبول، grouped report، الاختبارات، وفصل التنفيذ الوصفي عن التنفيذ المالي. |
| المالك / Chief Architect & Sports Quant | اشترط عدم استخدام closing في pre-match، ومنع إعلان الربحية عند crossing-zero، وأكد أن 2526 لا يدخل الاختيار أو الضبط. |
| المدقق | اختبر post-issued، closing، mismatch، market definition mismatch، protected holdout، والسوق غير الثنائي. |
| الضامن | شغّل suite المشروع وفحص أن الفشل يكون explicit بدل استكمال التقرير بصمت. |

## نتائج التحقق المحلي

بعد إضافة البوابة والتقرير المجمّع، اجتاز المشروع **89 اختبارًا**، وRuff، و`compileall`، و`git diff --check`. الاختبارات الاصطناعية موسومة في suite فقط، ولم تدخل أي قياس حقيقي أو تقرير ربحية.

## حدود الإصدار

هذا الإصدار لا يثبت الربحية ولا صلاحية استراتيجية مالية. ما زال benchmark الاقتصادي الحقيقي مؤجلًا ما لم يقدم المستخدم أو مصدر مرخص snapshots منفصلة تحمل وقت الالتقاط وprovenance وحقوق إعادة الاستخدام. لا يُسمح للطبقة الحالية بإنشاء stake sizing أو Kelly أو أوامر تنفيذ أو توصيات للمستخدم.

## التحسين التالي المقترح

بعد تثبيت البوابة، التحسين المنطقي التالي هو **snapshot ingestion adapter بواجهة provider-neutral** يقرأ ملفات metadata-only أو مصادر مرخصة خارج Git، ويصدر schema موحدًا وmanifestًا دون حفظ أسرار أو اختيار bookmaker بعد ظهور النتائج. لن يعتمد هذا التحسين على 2526، ولن يفتح benchmark اقتصاديًا قبل اجتياز شروط المصدر والترخيص والزمن.
